 AI Agent Observability for OpenCode

Code Shadow is a local-first OpenCode plugin that gives coding agents durable
engineering memory and operational guardrails. It observes sessions, edits,
tool calls, errors, tests, decisions, and task progress, then turns that data
into context an agent can use before it edits code.

The core idea is simple: an agent should know what happened before, estimate
the blast radius of a change, preserve evidence of verification, and refuse to
declare success while the work is still incomplete.

 Why this repository is different

- Persistent memory — SQLite-backed project history survives compaction and new sessions.
- Task Graph + Auto Plan — actionable user requests become structured tasks with meaningful steps.
- Counterfactual Planner — estimates impacted files, dependencies, historical breakage, and checks before edits.
- Evidence Ledger — verification commands become explicit verified or failed evidence.
- Change Contracts — active path boundaries can warn or block unsafe edits.
- Failure Memory — root causes and do-not-repeat guidance are reusable by future agents.
- Definition of Done — completion is guarded by steps, evidence, failures, contracts, and contradictions.
- TUI dashboard — live project health and agent activity without sending code to a cloud service.

 Quick start

bash
opencode plugin https://github.com/xuviga/code-shadow-ai-agent-observability --global


Or install the local checkout while developing the plugin:

bash
opencode plugin . --global --force
npm install
npm run typecheck
npm test


 Agent workflow

text
user request
  → auto task + plan
  → context router + counterfactual impact analysis
  → change contract
  → implementation
  → automatic evidence capture
  → definition-of-done gate
  → complete or handoff


 Adaptive edit-loop guard

The loop guard is deliberately progress-aware. Three successful mutations to
one file emit a warning, but different substantive edits remain allowed while
the agent is making progress. A successful test, typecheck, build, or other verification
command resets the file's suspicion state; a new user request resets it too.
The guard blocks only a strong no-progress signal: repeated identical content,
or a long sequence of five consecutive full writes to the same file without
verified progress. A sequence of distinct targeted edit operations remains
allowed, including after full rewrites, so an agent can repair a difficult
module one patch at a time. This protects against rewrite loops without
preventing normal iterative bug fixing.
