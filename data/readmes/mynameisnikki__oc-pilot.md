**A zero-dependency, offline-first gate for AI-generated code.** oc-pilot is a CLI, an MCP server and a CI guardrail in one Node.js 22+ package. Its job is not to write features. It mechanically verifies the code your agent wrote before it reaches `main`.

[English](README.md) · [Русский](README.ru.md) · [Integrations](docs/integrations.md) · [Security](SECURITY.md) · [Contributing](CONTRIBUTING.md) · [Changelog](CHANGELOG.md)

## The problem

AI agents are great engines with no brakes. They hallucinate dependencies that do not exist, weaken assertions until the suite is green, leak secrets into diffs, and turn a clean architecture into AI slop. Reviewing every agent diff by hand does not scale, and "the tests passed" is not a security argument.

## The solution

oc-pilot is the brake. It runs deterministic checks on the diff, gives your agent structured evidence through MCP, and blocks the merge when the evidence is bad.

- **Offline first.** Secret scanning, SAST, dependency checks and the code graph run locally. No code is sent to a model unless you explicitly call a model-backed command.
- **Agent native.** One MCP server exposes review, fix, test-fix, scan, preflight, query and sandbox tools to Cursor, Claude Code, OpenCode and any other MCP client.
- **CI ready.** `oc-pilot preflight` is a single gate with a non-zero exit code, GitHub annotations and a compact JSON report.

## See it work

[Open the asciinema cast](https://github.com/MyNameIsNikki/oc-pilot/blob/main/docs/demo.cast) of a 30-day oc-pilot session, or run the same loop locally:

```bash
oc-pilot battle "fix the retry logic" --apply --shadow --rounds 3
```

`battle` runs a coder and a hacker against the same diff. The coder patches; the hacker reviews, runs SAST, checks route authorization and looks for weakened tests. `--shadow` keeps the whole fight inside `.oc-pilot/shadow-tree`, a real detached git worktree. The diff lands in your working tree only after the round is green. Play the cast locally with `asciinema play docs/demo.cast`.

## Why oc-pilot?

- 🛡️ **Cryptographic receipts, not vibes.** `oc-pilot receipt --sign --key <file>` runs tests and preflight, records the commit, diff and results, then signs the receipt with Ed25519. `oc-pilot ready` verifies the signature when a public key is present. Receipts are opt-in; nothing is signed behind your back.
- 🧠 **Holographic context, not token dumps.** `oc-pilot pack --hologram` compiles a diff into three levels of detail: LOD 0 keeps changed files complete, LOD 1 hides bodies but keeps signatures and effects, LOD 2 lists export names. The agent gets the context it needs instead of a 100k-line dump.
- 🔥 **Zero dependencies.** Pure Node.js 22+, TypeScript ESM, no Python, no Docker, no native binaries. `npm install -g oc-pilot` is the whole setup.
- 🎮 **Gamified DX with teeth.** `bounty` renders ASCII WANTED posters for risky files, `roast` gives a Linus-style review of the diff, `brag` exports a self-contained HTML session report, and `cinema` turns a session into an asciinema cast or an HTML player.
- 🔒 **Offline-first security.** Secrets, hallucinated dependencies, SQL injection, SSRF, path traversal and XSS checks run without a network call. The model is optional, not the engine.
- 🕸️ **A real code graph.** `oc-pilot query "find(CallExpression).where(name, 'stripe').select(file, line)"` answers architecture questions without grep. It is a fast textual graph, not a full TypeScript AST.

## Quick start

```bash
npm install -g oc-pilot
oc-pilot setup --all
oc-pilot doctor
oc-pilot scan
```

`setup --all` writes native MCP configs for every supported client and preserves existing settings. `doctor` checks the installation, engine credentials, test discovery and MCP wiring. `scan` reads the current diff; on a clean tree use `oc-pilot scan --staged` or `oc-pilot scan --base origin/main`.

Node.js 22+ is required. Model-backed commands (`review`, `fix`, `roast`, `battle`) need OpenCode 2.x or an OpenAI-compatible endpoint; offline commands work without a model.

## Recipes

```bash
# Roast the AI diff before a human review
oc-pilot roast --staged --persona linus

# Verify a signed compliance manifest
oc-pilot compliance --verify

# Forecast when technical debt becomes unmaintainable
oc-pilot bankruptcy --explain

# Find the commit that introduced a security flaw
oc-pilot autopsy HEAD --depth 10

# Ask the code graph where a call lives
oc-pilot query "find(CallExpression).where(name, 'stripe').select(file, line)"

# Run a generated script with imports and side effects blocked
oc-pilot sandbox run scripts/demo.mjs

# Check the encrypted agent mesh
oc-pilot hivemind status
```

`bankruptcy` needs at least 10 commits and is a heuristic, not a promise. `sandbox run` isolates JavaScript in `node:vm`; it is not an OS sandbox for native code. `hivemind` speaks encrypted TCP, not WebRTC, and trusts peers only after an explicit `hivemind trust`.

## In CI

```yaml
name: oc-pilot
on: [pull_request]

jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npx -y oc-pilot preflight --base ${{ github.event.pull_request.base.sha }} --github
```

`preflight` checks secrets, deterministic SAST, route authorization, dependency health, weakened tests and the Slop Index delta. It exits non-zero on failure, so the branch protection rule does the rest. SAST and route checks skip test fixtures by default; pass `--include-tests` to scan them.

## Under the hood

No magic and no hidden cloud calls. A static import graph and a lightweight textual AST drive `query`, `preflight`, `scan`, `deps` and `test-guard`. `test-guard` catches the classic agent move: changing `expect(x).toBe(200)` to `expect(x).toBeDefined()` to make the build green. `fix --shadow` runs the patched tree in a real detached git worktree, so external compilers and test runners see the modified files; the diff lands only after a green run. `sandbox run` uses `node:vm` with blocked imports, blocked side effects and a hard timeout.

## How it works

1. `oc-pilot` collects the diff and project metadata.
2. It scans added lines for secrets and replaces detected values with `[REDACTED:<kind>]`.
3. It loads project rules from `.oc-pilot/rules.md` (optional).
4. It builds an input with `PROJECT_TYPE`, `RECIPE`, repository context, rules, the secret report, and `GIT_DIFF`.
5. With the OpenCode engine, a read-only agent can use `read`, `glob`, and `grep` to inspect call sites and contracts. `edit`, `shell`, web access, and external directories are denied.
6. The model returns a fixed Markdown schema. `oc-pilot` parses severity and emits JSON on request.
7. `--fail-on` and `--fail-on-secrets` turn findings into CI exit codes.

With `--no-repo-context`, the agent gets no tools. `oc-pilot` instead includes full changed files (`FULL_FILE_CONTEXT`) within the context budget.

## Engines

Choose where the model call goes. `opencode` is the default and gives the best review because the agent can read call sites and contracts. `openai` removes the OpenCode dependency: it calls any OpenAI-compatible `/chat/completions` endpoint and automatically includes the full changed files as context.

```bash
# Default: repo-aware OpenCode agent
oc-pilot review

# Any OpenAI-compatible API, no OpenCode required
export OC_PILOT_API_KEY="..."
oc-pilot review --engine openai --model deepseek-chat \
  --base-url https://api.deepseek.com/v1

# Local model through Ollama (no key needed on loopback)
oc-pilot review --engine openai --model qwen2.5-coder \
  --base-url http://127.0.0.1:11434/v1

# The same, through a preset
oc-pilot review --engine-preset ollama --model qwen2.5-coder
```

| Engine | Best for | Repository tools | Requires |
| --- | --- | --- | --- |
| `opencode` | Cross-file bugs and contract changes | Read, glob, grep (read-only) | OpenCode + provider auth |
| `openai` | Zero extra CLIs, CI, DeepSeek/OpenRouter/local models | No; full changed files are included | API endpoint and key |

The key is read from `OC_PILOT_API_KEY`, or `OPENAI_API_KEY` when the default variable name is used. Set `apiKeyEnv` to use another variable. Logs and errors never print the key. With the `openai` engine, `repoContext` is forced off and `FULL_FILE_CONTEXT` is added automatically.

### Engine presets

For the common OpenAI-compatible providers, `--engine-preset` fills in the base URL, the key variable and (where it is a sensible default) the model:

| Preset | Base URL | Key variable | Default model |
| --- | --- | --- | --- |
| `ollama` | `http://localhost:11434/v1` | `OLLAMA_API_KEY` (not needed on loopback) | `llama3.2` |
| `lmstudio` | `http://localhost:1234/v1` | `LMSTUDIO_API_KEY` (not needed on loopback) | — |
| `openrouter` | `https://openrouter.ai/api/v1` | `OPENROUTER_API_KEY` | — |

A preset switches the engine to `openai` unless you say otherwise, and explicit flags always win: `oc-pilot review --engine-preset ollama --model qwen2.5-coder` keeps the preset endpoint and overrides only the model.

### Anthropic engine

`--engine anthropic` talks to the Claude Messages API directly, without an SDK:

```bash
ANTHROPIC_API_KEY=sk-ant-... oc-pilot review --engine anthropic --model claude-sonnet-4-5
```

The system prompt is sent as a `system` block with `cache_control: {"type": "ephemeral"}`, so repeated reviews reuse the cached prefix. Requests use `anthropic-version: 2023-06-01` and `x-api-key`. Token usage is mapped onto the same cost table as the OpenAI engine, so `--max-cost` and `oc-pilot stats` work unchanged.

Slicing, the two-phase router and the response cache are `openai`-only; the Anthropic engine always sends one request per run.

### Smart slicing (`openai`)

When a diff is too large for a single prompt (300 000 characters), the `openai` engine does not truncate files away. Instead it groups the per-file diff blocks into slices that each fit the budget, runs one API call per slice with the same additional context, and merges the responses back into a single schema-compliant analysis (`meta.slices` shows how many calls were made). Up to three slices run in parallel and their answers are merged in the original file order. A single file whose diff exceeds the budget is sent as its own slice and only then truncated. Slicing applies to `review`, `test-fix`, `custom` and `commit --engine openai`; `fix` keeps a single prompt because it must return one patch.

### Retries

Transient failures are retried instead of failing the run: HTTP 408, 425, 429, 500, 502, 503 and 504 are attempted up to three times with an exponential delay (500 ms, 1 s, 2 s, capped at 8 s). A `Retry-After` header wins over the computed delay. Authentication errors, other 4xx responses, network errors and timeouts still fail immediately, because retrying them only burns time. Slice calls share the same policy.

### Two-phase routing (`openai`)

`review` can route through a cheap triage model before the main review call. The triage model sees the same input with a compact system prompt and answers with a single line: `TRIAGE: REVIEW` or `TRIAGE: LGTM`. Trivially safe diffs (docs, formatting, version bumps, renames) return `LGTM` and skip the main call entirely; everything else runs the full review. Any triage failure or unparsable answer falls back to the full review, so routing can only save money, never skip a real problem. Secret gating (`--fail-on-secrets`) is evaluated independently of the router.

```bash
oc-pilot review --router --router-model gpt-4.1-mini --engine openai --model gpt-4.1
```

Enable it per run with `--router`, or permanently with `routerEnabled: true` and `routerModel` in `.oc-pilot.json` (or `OC_PILOT_ROUTER` / `OC_PILOT_ROUTER_MODEL`). `--no-router` disables it for one run. The JSON report includes `meta.router` with the model, decision and duration.

### Provider-cache-friendly prompts

oc-pilot orders every prompt so the stable parts come first and the volatile `GIT_DIFF` comes last: instruction, project type, recipe, repository flags, additional context and the secret report are identical across slices, fix rounds and repeated reviews of the same change. Providers with prefix caching (OpenAI, DeepSeek, Anthropic, OpenRouter) reuse that stable prefix automatically, so the second and later calls on the same context are cheaper and faster. No configuration is needed.

### Response cache (`openai`)

The `openai` engine caches full model responses on disk. The cache key is the sha256 of the model, base URL, system prompt and input, so re-running the same command on the same diff (typical when wiring hooks, CI or scripts) costs zero tokens and returns instantly. Entries live in `.git/oc-pilot/cache/` — inside the repository metadata, never in the worktree or in commits.

The TTL defaults to 24 hours (`cacheTtlSeconds`, or `OC_PILOT_CACHE_TTL`; `0` disables caching). `--no-cache` bypasses the cache for one run, and `oc-pilot cache --stats | --prune | --clear` inspects and maintains it. `doctor --fix` prunes expired entries. The JSON report shows `meta.cache: "hit" | "miss"`. The cache only applies to the `openai` engine (triage, main and slice calls); OpenCode runs are never cached, and a cache error can never fail a review.

### Second opinion (`openai`)

`review --second-opinion` re-checks up to 10 critical findings with a second, skeptical model before failing the build. Each verdict is a single line: `VERDICT: CONFIRM` keeps the finding, `VERDICT: REJECT — <reason>` downgrades it to style and annotates the bullet with `[second opinion: rejected — reason]`. If the verifier errors or is unreachable, findings are kept as-is — verification never weakens a review on failure. Configure the verifier with `--second-opinion-model` / `--second-opinion-base-url` / `--second-opinion-api-key-env` or the config keys `secondOpinionEnabled`, `secondOpinionModel`, `secondOpinionBaseUrl`, `secondOpinionApiKeyEnv`; the result is reported in `meta.secondOpinion`.

### Usage limits and statistics

Every run and API call is recorded to `.git/oc-pilot/stats.jsonl` (findings, engine, exit code, cache hits). `oc-pilot stats` prints runs, API calls, cache hits and findings for today, the week and all time (`--clear` resets). A daily API-call budget can be enforced with `maxDailyApiCalls` or `OC_PILOT_MAX_DAILY_API_CALLS` (`0` disables it); once the limit of uncached calls is reached, the command exits 1 — cache hits never consume the budget. `oc-pilot day --since "1 day ago"` summarizes what the agent did: commits, churn per file, added/deleted lines and oc-pilot findings. A spend cap works the same way: `--max-cost 0.5` (or `maxCostUsd` / `OC_PILOT_MAX_COST`) adds up the estimated cost of today's uncached calls — tokens from the API response times the built-in price table — and refuses the next call once the cap is reached. Pricing is estimated, so treat it as a guard rail rather than an invoice; unknown models count as zero and cache hits are free.

### Agent rules awareness

If the project has an `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.cursorrules` or `.github/copilot-instructions.md`, oc-pilot includes it in every prompt (first match, up to 10 000 characters, secrets masked). This keeps the reviewer aware of the same conventions the coding agent follows. Disable with `agentRules: false` in the config or `OC_PILOT_AGENT_RULES=0`.

## Commands

### `review`

Reviews a git diff. By default it reviews all uncommitted changes (`git diff HEAD`).

```bash
oc-pilot review
oc-pilot review --staged
oc-pilot review --base main
oc-pilot review --include-untracked
oc-pilot review src/wallet.go --context "Balance must never be negative"
git diff | oc-pilot review --stdin
```

| Option | Purpose |
| --- | --- |
| `--staged` / `--unstaged` | Limit the diff to one side |
| `--base <ref>` | Review `<ref>...HEAD` |
| `--diff <file\|->` | Read a prepared unified diff |
| `--stdin` | Read the diff from stdin |
| `--include-untracked` | Add new files to the diff |
| `--context <text\|@file>` | Extra context for the model |
| `--no-secret-scan` | Disable secret scanning and redaction |
| `--fail-on-secrets` | Exit 3 on critical secrets |
| `--router` | Route through a cheap triage model first (`openai`) |
| `--no-router` | Disable routing enabled in the config |
| `--router-model <m>` | Triage model (default: `routerModel` from the config) |
| `--baseline` | Hide findings already recorded in `.oc-pilot/baseline.json` |
| `--update-baseline` | Record current findings as the baseline and exit |
| `--pr` | Post inline review comments to the PR (Actions REST or `gh`) |
| `--no-pr-inline` | Post a single summary comment instead of inline comments |
| `--pr-status` | Post a blocking commit status (`failure` on critical findings) |
| `--mr` | Post the review to a GitLab merge request (`CI_MERGE_REQUEST_IID`) |
| `--no-mr-inline` | Post a single summary note instead of inline discussions |
| `--mr-status` | Set the `oc-pilot` commit status in GitLab (`GITLAB_TOKEN`) |
| `--second-opinion` | Verify critical findings with a second model (`openai`) |
| `--second-opinion-model <m>` | Verifier model (default: `secondOpinionModel` or the main model) |
| `--require-tests` | Exit 3 when logic changed without tests |
| `--no-test-weakening` | Exit 3 when tests were weakened (skips, removed assertions) |
| `--interactive` | Ask per finding whether to hide it in the baseline (TTY) |

With `--baseline`, findings already recorded in `.oc-pilot/baseline.json` are hidden from the output and no longer affect the exit code, JSON, SARIF or PR comment — only new findings block. A finding fingerprint is `severity | file | normalized text`, without the line number, so known findings survive code shifts. `--update-baseline` rewrites the file from the current review and exits 0; `--interactive` hides findings one by one and appends them to the baseline. `--pr` posts the review to the current PR: inside GitHub Actions it uses the review API with `GITHUB_TOKEN` and attaches up to 25 findings as inline comments on their diff lines (grant `permissions: pull-requests: write`); findings that do not map to a changed line, and every run outside Actions, fall back to one summary comment (locally through `gh pr comment`, which must be installed and authenticated). `--no-pr-inline` forces that summary comment. `--pr-status` posts a commit status under the `oc-pilot` context - `failure` while critical findings remain, `success` otherwise - so a branch protection rule can require it (needs `statuses: write`). It works from text and SARIF runs alike.

Inside GitLab CI, `--mr` posts the review to the merge request: up to 25 findings become inline discussions anchored to their diff lines, and the summary always lands as a note. `CI_MERGE_REQUEST_IID`, `CI_PROJECT_ID` and `CI_API_V4_URL` identify the merge request, and `GITLAB_TOKEN` needs the `api` scope (`CI_JOB_TOKEN` cannot write notes). The discussion position needs `base_sha`/`start_sha`/`head_sha`: they are read from `CI_MERGE_REQUEST_DIFF_BASE_SHA`, `CI_MERGE_REQUEST_TARGET_BRANCH_SHA` and `CI_COMMIT_SHA`, and when those are absent the tool asks the merge request for its `diff_refs` instead. `--no-mr-inline` keeps the summary note only. Add `--mr-status` to set the `oc-pilot` commit status as well. Every part degrades to a warning when the pipeline context, the token or a single position is missing, so a review never fails because of a missing integration.

A minimal job looks like this:

```yaml
oc-pilot:
  image: node:22
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  script:
    - npm i -g oc-pilot
    - oc-pilot review --base "origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME" --fail-on critical --mr --mr-status
  variables:
    OC_PILOT_API_KEY: $OC_PILOT_API_KEY
    GITLAB_TOKEN: $GITLAB_TOKEN
```

Before the model runs, `review` also inspects the diff locally: newly added dependencies are checked for typosquats, unpinned versions and VCS/URL specs across npm, PyPI, Go, Cargo, RubyGems, Packagist, Maven/Gradle and NuGet manifests (`DEPENDENCY_CHANGES` hint, `meta.dependencies`); a large logic change (20+ added code lines) with no test files produces a `TEST_COVERAGE_HINT` (`--require-tests` turns it into exit 3, `meta.testDelta`); weakened tests produce a `TEST_WEAKENING` hint (skipped or focused tests, removed assertions without replacements, commented-out assertions, raised timeouts; `--no-test-weakening` turns it into exit 3, `meta.testWeakening`); and added lines matching prompt-injection heuristics (instruction overrides, role hijacking, prompt exfiltration, base64 blobs, invisible Unicode) produce a `PROMPT_INJECTION_RISKS` warning (`meta.injection`).

See [Second opinion](#second-opinion-openai) for the verification flow.

### Suppressing findings in code

An accepted trade-off should not come back as a finding on every review. Mark it at the source:

```go
func pay() {} // oc-pilot:ignore: nil is impossible for a legacy wallet
```

The marker suppresses a finding whose target is that line or the line right below it, so it also works as a comment on its own line above the code. `// oc-pilot:ignore-file: code generated by protoc` in the first ten lines silences the whole file. A reason is mandatory: a bare `oc-pilot:ignore` is ignored, the finding stays, and the run warns about it. Suppressed findings disappear from the text, JSON, SARIF and PR or MR comments and do not affect the exit code, while `meta.suppressed` lists each one with its file, line and reason. `oc-pilot:ignore-secret` belongs to the secret scanner and never hides a review finding.

### `test-fix`

Runs the detected test command, or reads a log, then explains the root cause and proposes a minimal fix.

```bash
oc-pilot test-fix
oc-pilot test-fix --command "go test ./..."
oc-pilot test-fix --log failures.log
npm test 2> failures.log; oc-pilot test-fix --log failures.log
```

A passing test run is skipped unless `--force` is used.

### `test-gen`

Turns a diff into tests that actually run. The model writes tests for the behavior changed in the diff, the patch is applied, the test command runs, and only the green result stays: a failing attempt is rolled back and the failure log goes back to the model as feedback.

```bash
oc-pilot test-gen --staged --apply
oc-pilot test-gen --staged --coverage --apply
oc-pilot test-gen --from-slop --apply
oc-pilot test-gen src/billing.ts --apply --rounds 1
oc-pilot test-gen --base main --json
oc-pilot test-gen --diff changes.diff
```

Without `--apply` the command only prints the patch. The patch may touch test files only (`*.test.ts`, `*.spec.ts`, `*_test.go`, `test_*.py`, or paths under `test/`); a production file in the patch rejects the whole round. Existing test files are protected unless `--force` is passed, so generated tests never overwrite hand-written ones. `--no-run` applies without executing the suite, `--keep-failing` keeps a red test file for debugging, and `--rounds <n>` (default 2) controls how many times a failure is sent back to the model.

`--coverage` narrows the request to changed lines that no test executed yet. The command reads an lcov, Istanbul JSON, Cobertura XML or Go cover profile report (`--coverage-file <path>` overrides the auto-detected `coverage/lcov.info`, `coverage/coverage-final.json`, `cobertura.xml`, `coverage.out` and similar files), intersects it with the lines added by the diff, and sends only those gaps to the model. When every changed line is already covered, it exits 0 without calling the model.

`--from-slop` ignores the diff and lets the slop scan choose the work: it looks for source files that have no test at all and ranks them by churn, duplicated blocks and unresolved TODOs. `--slop-files <n>` (default 3) caps how many files are sent. The command refuses to mix `--from-slop` with `--diff`, `--staged`, `--base`, `--coverage` or explicit paths, because those already define the input. When every source file has a test, it exits 0 without calling the model.

The JSON payload is `{applied, patch, files, status, tests, rounds, analysis, meta, coverage, targets}` with `status` equal to `pass`, `fail` or `not-run` and `coverage` holding `{report, format, uncoveredLines, gaps, missing}` (or `null` without `--coverage`); `targets` lists the slop-selected files with their scores and reasons (or `null` without `--from-slop`). The exit code is 1 while the tests stay red.

### `fix`

Asks the model for a unified diff, checks that it applies, and optionally applies it in the project. This is the only command that can modify your working tree, and only with `--apply`.

```bash
# Show the proposed patch and do not touch files
oc-pilot fix --diff changes.diff

# Apply, run tests, and keep the patch only when tests pass
oc-pilot fix --apply --command "npm test"

# Apply but keep the patch even when tests fail
oc-pilot fix --apply --command "go test ./..." --keep-on-test-failure

# Fix SAST findings in the changed files
oc-pilot fix --from-sast --staged --apply
oc-pilot fix --from-authz --staged --apply

# Emit GitHub Actions annotations for the findings
oc-pilot review --github
```

| Option | Purpose |
| --- | --- |
| `--apply` | Apply the patch to the working tree |
| `--command <cmd>` | Test command after applying; defaults to `testCommand` or auto-detection |
| `--no-tests` | Apply without running tests |
| `--keep-on-test-failure` | Do not revert a patch when tests fail |
| `--no-snapshot` | Skip the safety snapshot before applying |
| `--from-sast` | Fix high-severity SAST findings in the changed files, then rescan |
| `--from-authz` | Fix high-severity authorization findings in the changed routes, then rescan |

`fix` never commits or pushes. The patch is reverted when tests fail unless `--keep-on-test-failure` is used. Unrelated working-tree changes are not reverted.

Before applying, `fix` saves a snapshot under `.git/oc-pilot/snapshots/` (tracked changes as a binary patch plus copies of untracked files). Snapshots stay local: they are never committed or pushed. Restore the snapshot with `oc-pilot restore`; skip it with `--no-snapshot`.

With `--from-sast`, `fix` scans the changed files with the built-in SAST rules, asks the model for a patch that removes those findings, applies it, and rescans. The JSON payload gains `sast: {before, after, remaining}`; the exit code is 1 when high-severity findings remain. With `--from-authz`, the same loop targets route authorization findings (an unauthenticated route, an IDOR lookup, an admin path without a role) and the payload gains `authz: {before, after, remaining}`; `--from-sast` and `--from-authz` cannot be combined.

Generates GoDoc, RustDoc, JSDoc, Python docstrings, and similar comments without changing the code.

```bash
oc-pilot docgen src/core/prompt.ts
oc-pilot docgen "src/**/*.ts" --symbol buildPrompt
```

### `custom`

Runs a free-form analysis with an optional diff and context.

```bash
oc-pilot custom "Find data races" --git-diff
oc-pilot custom "Explain this module" --context @ARCHITECTURE.md
```

### `scan`

Offline secret scan. No model call.

```bash
oc-pilot scan
oc-pilot scan --staged --json
oc-pilot scan --all
git diff main...HEAD | oc-pilot scan --stdin

# SARIF 2.1.0 for GitHub Code Scanning
oc-pilot scan --staged --format sarif -o oc-pilot.sarif
```

Exit 1 means critical secrets were found. `--strict` also fails on warnings. `--format sarif` writes a SARIF 2.1.0 report (rules `oc-pilot/secret`, `oc-pilot/critical`, `oc-pilot/warning`) that GitHub Code Scanning can upload; secret previews stay redacted.

`--all` scans the whole tree instead of a diff. It respects `.gitignore` and `.oc-pilot/ignore`, skips binaries, `node_modules`, `dist` and files over 512 KB, and reports how many files were checked (`meta.filesScanned`).

### `preflight`

One offline verdict before a commit. Six checks run without a model and without network: secrets in the diff, a deterministic SAST pass over the changed source files (command and SQL injection, path traversal, SSRF, code injection, XSS and more), route authorization over the changed source files (an unauthenticated route, an IDOR lookup, an admin path without a role), dependency health scoped to the files the diff touches, weakened tests (`it.skip`, removed assertions, raised timeouts), and the Slop Index delta against a base ref.

```bash
oc-pilot preflight
oc-pilot preflight --staged
oc-pilot preflight --base main --max-delta 0
oc-pilot preflight --no-slop --fail-on-issue medium
oc-pilot preflight --staged --no-sast
```

Dependency issues are scoped: preflight reports only problems in files the diff changes or packages named in added lines, so a legacy repository does not fail on the first run. Findings recorded in `.oc-pilot/baseline.json` are hidden by default, so the gate reports only new problems; `receipt` uses the same baseline. `--fail-on-issue` (default `high`) sets the gate for SAST, route authorization and dependency severity, and `--max-delta` (default 10 points) sets the Slop Index gate; each check can be disabled with `--no-secret-scan`, `--no-sast`, `--no-authz`, `--no-deps`, `--no-tests` or `--no-slop`. The exit code is 1 if any check fails and 0 otherwise, so one CI step replaces six.

The JSON report is `{status, checks, diff}`, where each check carries `{id, label, status, summary, details}` with `status` equal to `pass`, `fail` or `skip`.

### `receipt`

Turns "it works on my machine" into a checked claim. A receipt runs the tests and the preflight (including SAST and authz), then records the result together with the commit SHA, branch, dirty state, diff stats, and the exact commands. It is written to `.git/oc-pilot/receipt.json`, so it never ends up in the working tree. Pass `--no-sast` or `--no-authz` to skip a check for a change where it does not apply.

```bash
oc-pilot receipt --staged
oc-pilot receipt --staged --no-sast
oc-pilot receipt --json
oc-pilot receipt --verify
oc-pilot receipt --verify --receipt path/to/receipt.json
oc-pilot receipt --keygen receipt.key
oc-pilot receipt --sign --key receipt.key
oc-pilot receipt --verify --public-key receipt.key.pub
```

The file is sealed with a SHA-256 hash of its body. `--verify` recomputes the hash and compares the commit with the current `HEAD`, so an edited file or a receipt from an older commit is reported as invalid: `{path, ok, hashOk, stale, commit, head, signature, reason?}`. The exit code is 1 when the tests fail, the preflight fails or the receipt does not verify.

A hash proves integrity, not authorship. `--sign` signs the hash with an Ed25519 key: `--keygen <file>` writes a private key (mode 0600) and `<file>.pub`; `--key` or `OC_PILOT_RECEIPT_KEY` points at the private key; the receipt gains a `signature` field. Verification checks the signature when a public key is available: `--public-key <file>`, `OC_PILOT_RECEIPT_PUBLIC_KEY`, or the committed `.oc-pilot/receipt.pub`. The `signature` status is `valid`, `invalid`, `missing` or `unchecked`; an unsigned receipt fails verification when a key is supplied. `ready` verifies the signature too when `.oc-pilot/receipt.pub` exists. Keep the private key outside the repository.

A receipt carries `{version, tool, toolVersion, createdAt, commit, branch, dirty, diff, files, tests, preflight, hash, signature?}`. `tests` is `{command, exitCode, timedOut, durationMs, passed, outputTail}` or `null` with `--no-run`; `preflight` is the same report `preflight` prints. Outside a repository the receipt can only be written to an explicit path with `--out`.

### `ready`

Scores how ready a repository is for an AI agent. One offline number from 0 to 100 across nine checks: tests (15), lockfile (10), git hooks (15), Slop Index (15), a fresh receipt (10), agent instructions (10), CI (5), config (5) and security (15). Each check is `pass`, `warn` or `fail` and earns 100%, 50% or 0% of its weight. The security check runs the deterministic SAST and route-authorization rules over the repository and respects `.oc-pilot/baseline.json`. No model call, no network, but it does require a git repository.

```bash
oc-pilot ready
oc-pilot ready --json
oc-pilot ready --badge
oc-pilot ready --fail-under 85
oc-pilot ready --fix
oc-pilot ready --fix --dry-run
oc-pilot ready --fix --receipt
```

The score maps to a grade: 85 and above is `agent-ready`, 65 and above `almost`, 40 and above `risky`, anything lower `not-ready`. `--badge` prints a shields.io markdown badge for the README, and `--fail-under <n>` exits with code 1 below the threshold, so the score can gate a pull request.

`--fix` applies only safe, offline repairs: it installs the `pre-commit` hook when no hook exists, writes `.oc-pilot.json` with the detected test command, and creates `AGENTS.md` with the project commands. A foreign hook, an existing config or existing agent instructions are never overwritten; the report lists those as skipped together with checks that need a human, such as the receipt, the lockfile and the Slop Index. `--dry-run` prints the plan without touching the tree, and the score is recomputed after the fixes.

`--receipt` turns `--fix` into a full loop: after the repairs it runs the test command, runs the preflight and saves a receipt for `HEAD`, so the receipt check can pass in the same run. It requires `--fix`; without a test command the receipt is listed as skipped. A failed test run or a failed preflight still produces a receipt — the report says which part failed.

The JSON payload is `{score, grade, checks, commit}`; each check is `{id, label, status, points, max, detail}`, where `detail` names the file that earned or lost the points and the command that fixes it. With `--fix` the payload also carries `fix: {applied, dryRun, fixes, skipped, receipt}`, where `receipt` is `{path, testsPassed, preflight}` or omitted.

### `mutate`

Mutation testing answers a harder question than coverage: do the tests actually catch bugs? The command flips comparison and boolean operators in the changed source files, runs the test suite against each mutant and counts how many mutants the tests killed. A surviving mutant is a line the suite executes but does not really check.

```bash
oc-pilot mutate --staged
oc-pilot mutate --base main --max-mutants 10
oc-pilot mutate src/billing.ts --min-score 80
oc-pilot mutate --diff changes.diff --json
```

Operators are `===`/`!==`, `==`/`!=`, `>=`/`<`, `<=`/`>`, `&&`/`||` and `true`/`false`; strings and comments are masked, so only real code is mutated. `--max-mutants <n>` caps the run (default 20, max 500) because every mutant executes the whole suite. `--min-score <n>` exits with code 1 when the mutation score is below the threshold, which makes it a CI gate. A timeout counts as a kill: the mutant changed observable behavior.

The JSON payload is `{command, files, sites, mutants, killed, survived, timedOut, score, truncated, durationMs}`; each mutant is `{file, line, column, operator, original, replacement, status, durationMs}` with `status` equal to `killed`, `survived` or `timeout`.

### `flaky`

Runs the test command several times and compares per-test results. A test that passes in some runs and fails in others is flaky; one that fails every time is simply broken. The command never calls a model: it only runs the suite and parses the output.

```bash
oc-pilot flaky
oc-pilot flaky --runs 5
oc-pilot flaky --shuffle --command "node --test {files}"
oc-pilot flaky --command "go test ./..." --json
oc-pilot flaky --fail-on-flaky
```

`--runs <n>` defaults to 3 and caps at 10. `--command` overrides `testCommand` from `.oc-pilot.json` and the detected test command. `--fail-on-flaky` exits with code 1 when at least one test flipped, which makes it usable as a CI gate.

`--shuffle` turns the run into an order test. It requires `{files}` in `--command`, collects the test files from the repository, shuffles them with a seeded PRNG and substitutes the list into the command. Every run gets a fresh seed derived from the base one, so a test that fails only after a particular neighbour shows up as flaky. `--seed <value>` fixes the base seed when you need to reproduce a failure.

Per-test results are parsed from the Node test runner spec reporter, TAP, Go (`--- PASS`/`--- FAIL`), pytest (`PASSED`/`FAILED`) and Jest/Vitest (`✓`/`✕`). If the output carries no recognizable markers, `parsed` is false and the report only tells you that the exit codes were compared.

The JSON payload is `{command, runs, completed, parsed, tests, flaky, failing, shuffle}`; each test is `{name, passes, failures, status}` with `status` equal to `flaky`, `failing` or `passing`. With `--shuffle`, `shuffle` is `{seed, files}`.

### `authz`

Authorization review of HTTP routes: a route that never checks the session, an object fetched by an id from the request without an ownership check (IDOR), and an admin path without a role guard. It reads the changed source files and never calls a model.

```bash
oc-pilot authz --staged
oc-pilot authz --public /health,/login
oc-pilot authz --staged --fail-on-issue medium
oc-pilot authz --staged --format sarif -o authz.sarif
```

Express, Fastify and Koa route calls (`app.get`, `router.post`, ...) are recognized, plus Next.js `app/**/route.ts` and `pages/api/**`. A handler passed by reference (`router.get("/x", controller.list)`) is skipped because the guard may live in the controller. Routes under `/health`, `/login`, `/signup`, `/public`, `/webhooks`, `/oauth` and similar are treated as public; `--public <prefixes>` extends that list.

Suppress a deliberate exception on the route line or the line above:

```js
// oc-pilot:authz-ignore idor: the gateway scopes the query by tenant
router.get("/users/:id", handler);
```

A suppression without a reason is ignored. `--ignore <rules>` skips whole rules and `--no-suppressions` disables inline suppressions.

`--fail-on-issue <high|medium>` sets the exit threshold (default `high`). `--format sarif` emits SARIF 2.1.0 with the rule id, method and route.

`--baseline <file>` hides findings already recorded in `.oc-pilot/baseline.json`, so only new findings fail the run; `--update-baseline` writes the current findings to that file and exits with code 0, which lets a legacy repository adopt the gate without fixing everything at once. The baseline stores SHA-256 fingerprints of the rule, file and snippet (or method and route for `authz`), so entries survive line moves. `preflight` and `receipt` read the same default baseline.

The JSON payload is `{files, routes, findings, suppressed, summary}`; each route is `{file, line, method, route, public}` and each finding adds `{rule, severity, method, route}` to the location. With `--baseline` the payload adds `baselineSuppressed`; with `--update-baseline` it adds `baseline: {path, updated, entries}`.

### `sast`

Deterministic static analysis of the changed files: command and SQL injection, path traversal, SSRF, code execution, XSS, open redirects, disabled TLS verification, wildcard CORS, prototype pollution, weak hashes and JWT `none`. No model call, no network: the same diff always produces the same findings.

```bash
oc-pilot sast --staged
oc-pilot sast --base main --fail-on-issue medium
oc-pilot sast src/server.ts --json
oc-pilot sast --staged --format sarif -o sast.sarif
```

The analysis is taint-aware but heuristic: a sink is reported when request data (`req.query`, `req.body`, `req.params`, headers, cookies, `userInput`, `untrusted*`) or a template interpolation reaches it within the same expression. Constants and parameterized queries are not reported. `path.resolve`, `path.normalize`, `path.basename` and `path.join` suppress path traversal findings.

Suppress a deliberate exception on the finding line or the line above:

```js
exec(req.query.cmd); // oc-pilot:sast-ignore command-injection: admin-only endpoint
```

A suppression without a reason is ignored. `--ignore <rules>` skips whole rules, `--no-suppressions` disables inline suppressions for an audit run.

`--fail-on-issue <high|medium|low>` sets the exit code threshold (default `high`). `--format sarif` emits SARIF 2.1.0 for GitHub code scanning and other SARIF consumers.

`--baseline <file>` hides findings already recorded in `.oc-pilot/baseline.json`, so only new findings fail the run; `--update-baseline` writes the current findings to that file and exits with code 0, which lets a legacy repository adopt the gate without fixing everything at once. The baseline stores SHA-256 fingerprints of the rule, file and snippet, so entries survive line moves. `preflight` and `receipt` read the same default baseline.

The JSON payload is `{files, findings, suppressed, summary}`; each finding is `{rule, severity, file, line, column, message, snippet}` and `summary` counts `high`, `medium`, `low`. With `--baseline` the payload adds `baselineSuppressed`; with `--update-baseline` it adds `baseline: {path, updated, entries}`.

### `deps`

Offline health audit of npm, pnpm and yarn dependencies. No model call, no network.

```bash
oc-pilot deps
oc-pilot deps --json
oc-pilot deps --fail-on-issue high
oc-pilot deps --ignore lint-staged
oc-pilot deps --fix --dry-run
oc-pilot deps --fix
oc-pilot deps --why qs
oc-pilot deps --audit --fail-on-vuln high
oc-pilot deps --audit --offline
oc-pilot deps --sbom sbom.json
```

It compares `package.json` with what the code actually imports and with the lockfile the project uses: `package-lock.json`, `pnpm-lock.yaml` or `yarn.lock`.

- **phantom** (high) — a package is imported but not declared, so a clean install or CI fails;
- **unused** (medium) — declared but never imported or mentioned in scripts;
- **misplaced** (low) — used only by tests but listed in `dependencies`;
- **duplicate** (low) — two libraries from the same group solve one job (`moment` and `dayjs`);
- **unpinned** (medium) — `*`, `latest` or an empty spec;
- **vcs** (high for git/URL, low for `file:`) — a dependency from git, a URL or a local path;
- **lockfile** (high) — declared but missing from the project lockfile, so a clean install fails (`npm ci`, `pnpm install --frozen-lockfile` or `yarn install --immutable`).

`--fail-on-issue <high|medium|low>` turns the audit into a CI gate (exit 1). `--ignore <names>` accepts a comma-separated list for false positives, for example when a package is loaded dynamically. Workspace packages (`packages/*`) and `@types/*` are handled; peer dependencies are not reported as unused.

`--fix` repairs what can be decided offline: a package used only by tests moves to `devDependencies`, an imported-but-undeclared package is added with the version already resolved in the lockfile (to `devDependencies` when every importer is a test), and a floating `*`/`latest` spec is pinned to the lockfile version. Nothing is invented: a phantom import without a lockfile entry, an unused package, a duplicate or a vcs dependency is listed as skipped with the reason. `--dry-run` prints the plan without touching `package.json`. After writing, the audit re-runs, so the exit code reflects the fixed state.

`--why <name>` answers the question that comes before any cleanup: where does this package actually come from. It reads `package.json` and the lockfile locally and prints the declared field and spec, the files that import it, the packages that depend on it, every installed version and copy count, and the dependency chains from the root. A package that is neither declared, installed nor imported exits with code 1. `--why` cannot be combined with `--fix`.

`--audit` adds known vulnerabilities and licenses. It asks OSV (`api.osv.dev`) for every locked package, reports CVE/GHSA ids, severity and the first fixed version, and caches answers in `.oc-pilot/osv-cache.json` for 24 hours. `--offline` uses the cache without touching the network and fails when the cache is empty. `--osv-url` points the query at a mirror. `--fail-on-vuln <critical|high|medium|low>` turns the result into a security gate: the command exits with code 1 when any vulnerability reaches the threshold. Licenses are read from installed `node_modules` manifests; strong copyleft, proprietary and unknown licenses are listed, and packages without an installed manifest are counted as `missing` instead of guessed.

`--sbom <file>` writes a CycloneDX 1.5 software bill of materials for every locked package, with npm purls, relative to the project root. It needs no network.

The JSON payload is `{packageName, declared, imported, scannedFiles, truncated, lockfile, issues}`; with `--fix` it gains `fix: {applied, dryRun, fixes, skipped}`, with `--why` the command prints a single `DependencyWhy` object: `{name, versions, copies, declared, importedBy, dependents, chains}`, with `--audit` it gains `audit: {checked, unchecked, vulnerabilities, online, stale, cachePath, licenses}`, and with `--sbom` — `sbom: <path>`.

### `commit`

Generates a Conventional Commits message from staged changes and optionally commits it. The model also sees the last 10 commit subjects, so the message matches the project's existing style.

```bash
oc-pilot commit               # print the message
oc-pilot commit --apply       # commit staged with the generated message
oc-pilot commit --json        # machine-readable output
```

`--apply` works only with staged changes and is blocked (exit 3) when the diff contains critical secrets; pass `--allow-secrets` to override. With `--engine openai` an oversized diff is split into per-file slices (see Engines) and the message covers all of them.

### `install-hook`

Installs native git hooks without husky or any dependency. The managed `pre-commit` hook runs `oc-pilot preflight --staged`: secrets, SAST, route authorization, dependency health scoped to the change, test weakening and the Slop Index delta. `--pre-push` also installs a `pre-push` hook that runs `oc-pilot review --fail-on critical --fail-on-secrets`. Pass `--scan` to keep a lighter pre-commit that only runs `oc-pilot scan --staged`.

```bash
oc-pilot install-hook
oc-pilot install-hook --scan
oc-pilot install-hook --pre-push
oc-pilot install-hook --uninstall
```

Hooks are opt-in and reversible. A hook that does not belong to oc-pilot is never overwritten unless `--force` is passed, and then the old file is kept as `<hook>.oc-pilot.bak`. Every managed hook is stamped with a marker; hooks written by older versions are reported as outdated by `oc-pilot doctor` and upgraded in place with `oc-pilot doctor --fix`. Set `OC_PILOT_SKIP=1` to bypass the hooks for a single command. The hook prefers `OC_PILOT_BIN`, then `./node_modules/.bin/oc-pilot`, then `oc-pilot` from `PATH`; if none is found, it prints a warning and skips the check. `core.hooksPath` and worktrees are respected.

### `restore`

Restores the working tree from the latest snapshot taken before `fix --apply`.

```bash
oc-pilot restore          # latest snapshot
oc-pilot restore --list   # list saved snapshots
oc-pilot restore <id>     # a specific snapshot
```

Snapshots live under `.git/oc-pilot/snapshots/` and never enter commits. Restore refuses to run when the branch head has moved since the snapshot, so committed work is never lost. The staged/unstaged split is not restored, and untracked files created after the snapshot are not deleted.

```bash
oc-pilot cache            # entries, size, expired count
oc-pilot cache --prune    # delete expired entries
oc-pilot cache --clear    # delete everything
```

The cache only works inside a git repository and only applies to the `openai` engine.

```bash
oc-pilot stats
oc-pilot stats --json
```

### `day`

A local activity digest: what was committed since a point in time, which files churned most, lines added/deleted, and the oc-pilot findings for that period.

### `impact`

Shows where else the symbols you changed are used. It extracts function, method, class, type and interface declarations from the diff (both added and removed lines, so renames show up under both names) and greps tracked and untracked files for them. This is a text search, not AST analysis, so it can over-report; it never fails the build.

```bash
oc-pilot impact
oc-pilot impact --staged --json
```

`--json` returns `symbols`, `references`, `scannedFiles` and `touchedFiles`, which is the shape agents want when they need to know what else a change might break.

### `explain`

Explains the findings of the previous review for one place in the code. Every `review` run stores its findings in `.git/oc-pilot/last-review.json`; `explain` looks up the finding on the given line, or the nearest one within three lines, and prints it next to a snippet of the current file. Secrets in the snippet are redacted by the same scanner as everywhere else.

```bash
oc-pilot explain src/wallet.ts:42
oc-pilot explain src/wallet.ts:42 --json
```

Without a line number, or when nothing matches, it falls back to every finding in that file, so the command stays useful when the file shifted.

### `reviewers`

Suggests who should review the current diff. For every changed file it walks the recent commits that touched it, counts the authors and picks the top candidates; bots are skipped. `CODEOWNERS` from `.github/CODEOWNERS`, `CODEOWNERS` or `docs/CODEOWNERS` is read and matched with the same last-rule-wins semantics as GitHub and GitLab.

```bash
oc-pilot reviewers --base main
oc-pilot reviewers --staged --limit 5 --exclude renovate
oc-pilot reviewers --base main --json -o reviewers.json
```

`--depth` looks further back than the default 50 commits. `--json` returns the files, the candidates (`name`, `email`, `commits`, `files`, `share`) and the matched `codeowners`, which is enough to fill `gh pr create --reviewer`.

### `replay`

Re-renders the last saved review without calling a model. Every `review` writes `.git/oc-pilot/last-review.json`, so a SARIF report or a PR comment can be regenerated for free, or handed to a colleague.

```bash
oc-pilot replay
oc-pilot replay --format sarif -o report.sarif
oc-pilot replay --as md -o pr-comment.md
oc-pilot replay --in saved.json --fail-on critical
```

`--format` accepts text, json and sarif; `--as` adds md for the PR comment body. `--in` reads any file with a `findings` array. The exit code follows `--fail-on`, exactly as in `review`.

### `slop`

Measures the entropy that fast, model-assisted coding leaves behind. `oc-pilot slop` scores a repository from 0 (clean) to 100 (rotten) without an API key, a model or network access: it needs only git and the working tree.

| Category | What it finds | Max |
| --- | --- | --- |
| Duplicates | Blocks of 72 or more tokens repeated across two different files | 30 |
| Dead code | Exports whose name appears in no other file (type-only exports and entry points are skipped) | 25 |
| Churn without tests | Files touched by five or more commits while tests changed in fewer than 40% of them | 25 |
| TODO graveyard | `TODO`, `FIXME`, `HACK` and `XXX` inside comments, weighted by age from `git blame` | 20 |

```bash
oc-pilot slop
oc-pilot slop --since origin/main --max-delta 10
oc-pilot slop --json -o slop.json
oc-pilot slop --badge -o slop.svg
```

`--since <ref>` compares the working tree with a revision and reports what this branch introduced and removed per category, plus `deltaPoints`. The delta matters more than the absolute number: a repository can sit at 50 and still be stable.

Other flags: `--limit` (items per category), `--since-days` (churn and blame window, default 30), `--exclude` (globs or substrings), `--no-blame` (skip `git blame`, much faster), `--max-index` and `--max-delta` (exit code 3 when exceeded), `--badge` (shields-style SVG), `--json`.

False positives go to `.oc-pilot/slopignore`: one glob or substring per line, `#` starts a comment. Comments and string literals are stripped before analysis, and test files, generated files and lock files are skipped. The score is a heuristic, not a verdict.

### `setup`

Configures an MCP client to launch `oc-pilot-mcp`. Existing server entries and unrelated settings are preserved. It writes configs for Claude Code, Codex, Cursor, Gemini CLI, OpenCode, VS Code, Windsurf, ZCode, and any client that reads `.agents/mcp.json`. By default it points at the current installation; `--npx` writes a version-pinned `npx -y oc-pilot@<version> mcp` entry instead. Generated servers start read-only; add `--allow-write` if the agent should apply patches and run tests.

```bash
# Project-local Claude Code config (.mcp.json)
oc-pilot setup --client claude --local

# OpenCode and Cursor in one run
oc-pilot setup --client opencode --client cursor --local

# Global config, or print without writing
oc-pilot setup --client codex --global
oc-pilot setup --client claude --local --print

# Remote HTTP server with a bearer token
oc-pilot setup --client claude --local \
  --http https://oc-pilot.example.com/mcp --token "$OC_PILOT_MCP_TOKEN"
```

| Option | Purpose |
| --- | --- |
| `--client <name>` | `claude`, `codex`, `cursor`, `gemini`, `opencode`, `vscode`, `windsurf`, `zcode`, `agents`; repeatable |
| `--all` | Configure every supported client |
| `--global` | Write user-level config (project is the default) |
| `--local` | Force the current installation path |
| `--npx` | Force a version-pinned `npx` command |
| `--allow-write` | Let the client apply patches and run tests |
| `--print` | Print the config instead of writing it |
| `--json` | JSON plan for automation |
| `--http <url>` | Configure a remote Streamable HTTP endpoint |
| `--token <value>` | Enable bearer auth; the client reads the secret from `OC_PILOT_MCP_TOKEN` |
| `--cwd <dir>` | Project directory stored in the server args |
| `--force` | Replace an existing `oc-pilot` entry |

`setup` never writes the bearer token into a client config. It writes an `OC_PILOT_MCP_TOKEN` reference; export the secret in the environment that launches the client.

`setup` writes only MCP client config. It does not install packages or change your source. With no `--client`, it detects Claude Code, Codex, Cursor, Gemini CLI, OpenCode, VS Code, Windsurf, ZCode, and `.agents` clients from installed commands and config directories.

### `doctor`

One command that explains why a setup is not working:

```bash
oc-pilot doctor
oc-pilot doctor --json
oc-pilot doctor --engine openai --model deepseek-chat
oc-pilot doctor --fix
```

It checks Node, the active engine, API credentials, git and repository state, the detected test command, project rules, oc-pilot git hooks and the response cache, and every MCP client config. `--fix` refreshes outdated oc-pilot hooks (a backup of the previous file is kept) and prunes expired cache entries; foreign hooks are never touched and are reported instead. Errors return exit code 1; `--strict` also fails on warnings. No secret values are printed.

### `init`

```bash
oc-pilot init
oc-pilot init --preset node
oc-pilot init --hooks
```

Creates `.oc-pilot.json`. It does not overwrite an existing config unless `--force` is passed. With `--preset <a,b>` it also writes a curated `.oc-pilot/rules.md` for the stack. One or more presets can be combined, e.g. `--preset react,security`:

`base` (language-agnostic), `node`, `react`, `next`, `vue`, `svelte`, `angular`, `typescript`, `python`, `go`, `rust`, `java`, `kotlin`, `csharp`, `swift`, `php`, `ruby`, `flutter`, `elixir`, `zig`, `scala`, `security` (cross-stack hardening), `devops` (Docker, CI, infrastructure).

The rules file is a normal project rules file - edit it freely.

`--hooks` installs the git hooks from `install-hook`: `preflight --staged` on commit and `review` on push. Existing hooks are backed up, and a missing hook directory is only a warning, so `init` never fails because of it.

## Project rules

Add a `.oc-pilot/rules.md` at the project root, or point to one with `--rules` / the `rules` config field:

```markdown
- Keep handlers thin; business logic belongs in services.
- Errors must wrap the original cause.
- Never log request bodies or tokens.
- Prefer table-driven tests.
```

Rules are added to every recipe. They are scanned and redacted like any other project content, unless `--no-secret-scan` is used.

## Secret scanning

The scanner looks at added diff lines and common source-file patterns:

- private key blocks;
- OpenAI, Anthropic, Hugging Face, Groq, Google, GitHub, GitLab, npm, PyPI, Slack, Discord, Telegram, Stripe, SendGrid, DigitalOcean, and AWS keys;
- Azure storage account keys;
- JWTs, credentials in URLs, and sensitive `.env` assignments;
- high-entropy assignments (Shannon entropy over 4 bits for values of 20+ characters) reported as critical.

To silence a false positive, add path globs to `.oc-pilot/ignore` (one per line, `#` starts a comment), or append the inline marker to the source line:

```
# .oc-pilot/ignore
fixtures/**
docs/examples/**

# inline, any language
const TOKEN = "sk-proj-..."; // oc-pilot:ignore-secret
```

Ignore rules are path- and line-scoped, apply to every scanning point (diff, rules, docgen, full-file context), and never disable scanning for the rest of the project.

Detected values never appear in full in logs or JSON. The model receives `[REDACTED:<kind>]` and a masked preview. Review the provider's data policy before sending proprietary code.

`--no-secret-scan` and `redactSecrets: false` disable this protection for the diff, rules, and `FULL_FILE_CONTEXT`. Use them deliberately.

## MCP server

`oc-pilot-mcp` exposes the same recipes as MCP tools over stdio. This is the recommended way to embed oc-pilot in an agent: the agent calls a tool, and no prompt needs to be copied.

Besides tools, the server exposes read-only MCP resources: `oc-pilot://config` (resolved configuration), `oc-pilot://rules` (project rules with secrets redacted), `oc-pilot://prompt/en` and `oc-pilot://prompt/ru` (the built-in system prompts), and `oc-pilot://version`. `oc-pilot://slop` returns the Slop Index as JSON without calling a model. Resource templates cover live data: `oc-pilot://diff/{mode}` (staged/unstaged/head diff, secrets redacted), `oc-pilot://scan/{mode}` (offline secret scan as JSON) and `oc-pilot://file/{+path}` (any project file up to 2 MB with detected secrets redacted). Hosts can list them with `resources/list` and `resources/templates/list`.

Tools: `review`, `invariants`, `test_fix`, `fix`, `test_gen`, `docgen`, `custom`, `scan`, `commit`, `stats`, `slop`, `mutate`, `fuzz`, `bankruptcy`, `query_ast`, `sandbox`, `hivemind_status`, `flaky`, `impact`, `deps`, `coverage`, `reviewers`, `test_guard`, `env_sync`, `mock_leak`, `ecosystem_verify`, `pack`, `pack_hologram`, `zoom_symbol`, `contract_drift`, `anti_regression`, `boundaries`, `test_plan`, `compliance_verify`, `brag`, `battle`, `cleanup`, `arch_diff`, `roast`, `cinema`, `bounty`, `autopsy`, `echo`, `sast`, `authz`, `preflight`, `honeypot`, `alien_dna`, `hyper_chamber`, `butterfly`, `blindfold`, `antibody`, `polygraph`, `passport`, `oracle`, `vaccine`, `mitosis`, `intent`, `scalpel`, `mayday`, `clairvoyant`, `hemorrhage`, `cuckoo`, `chronos`, `beacon`, `quarantine`, `mirage`, `warden`, `tribunal`, `skeptic`, `apoptosis`, `scan_injection`, `ready`, `receipt_verify`. `scan` accepts `all: true` to sweep the whole repository instead of the diff. `slop` runs the offline Slop Index and accepts `since`, `since_days`, `limit`, `exclude` and `no_blame`. `mutate` runs mutation testing on the changed code, accepts `command`, `max_mutants` and `min_score`, and returns the score plus every surviving mutant; a score below `min_score` is a normal result with exit code 1. `flaky` runs the test command several times and compares per-test results, accepting `runs`, `command`, `fail_on_flaky`, `shuffle` and `seed`; it never edits source files itself but does run the project's tests. `impact` lists the declarations the diff changed or removed and every untouched file that still mentions them, accepting the same source flags; the search is textual, so comments and strings can match. `deps` audits declared, imported and locked dependencies, explains a chain with `why`, adds OSV vulnerabilities and licenses with `audit`, and can rewrite `package.json` with `fix` or emit a CycloneDX SBOM; `fix` and `sbom` write files. `coverage` compares changed lines with a local lcov, Istanbul, Cobertura or Go coverage report and returns uncovered lines, missing files and a gate on `fail_under` or `max_uncovered`. `reviewers` ranks the authors who touched the changed files, lists CODEOWNERS owners and accepts `limit`, `depth` and `exclude`; it uses git history only. `test_guard` runs the offline anti-cheating check on the diff: skipped, focused or deleted tests, removed or commented assertions, raised timeouts, strict matchers replaced by existence checks, `@ts-ignore` and empty catch blocks; with `fail_on_weakening` a finding returns exit code 1. `env_sync` compares the environment variables added by the diff (`process.env`, `import.meta.env`, `Deno.env`, `Bun.env`) with the local `.env` files and `.env.example`/`.sample`/`.template`: missing definitions fail with `fail_on_missing`, and defined but undocumented variables warn. `mock_leak` scans added production code for forgotten stubs and hardcode: local paths, test tokens, `if (true)`/`if (false)`, mock/fake/stub identifiers, mock comments and localhost URLs; `fail_on_leak` returns exit code 1 at the chosen severity. `ecosystem_verify` checks that named imports from the changed files exist in the installed package entry or its `.d.ts`, and flags packages that are neither installed nor declared; with `online` it also checks the age and weekly downloads of newly added npm packages, and `fail_on_issue` returns exit code 1 at the chosen severity. `pack` builds a compact context bundle for a task: project rules, changed-file signatures, related references and an optional test log, capped by `budget` characters; it never edits files. `contract_drift` compares changed TypeScript interfaces, Zod objects, Prisma models, Pydantic models and JSON Schema with the previous version, flags removed or newly required fields and type changes, and reports untouched consumers that still use a removed field; `fail_on_drift` returns exit code 1 at the chosen severity. `anti_regression` compares the lines added by the diff with lines a human explicitly deleted in git history, cites the deleting commit and flags re-added code or imports; `fail_on_regression` returns exit code 1. `boundaries` checks added imports against `.oc-pilot/architecture.json` layer rules, reports the file, line, import and rule reason, and `fail_on_violation` returns exit code 1 when a layer boundary is crossed. `test_plan` selects the test files affected by the diff from a static import graph: changed tests, direct and transitive importers, naming matches and symbol references, with uncovered changed files reported and an optional `fail_on_uncovered` gate. `compliance_verify` checks a signed audit manifest for the current commit: SHA-256, commit, previous-manifest hash chain and optional Ed25519 signature; a missing, edited or broken manifest is a normal result with exit code 1. `brag` builds a self-contained HTML or SVG session report from stats, git history, the last review and the receipt; it uses inline assets only, never calls a model or the network, and `no_paths` hides file locations. `test_gen` asks the model for tests that cover the changed code; with `apply` it writes test files, runs the suite and reverts failing tests unless `keep_failing`, while `coverage` narrows generation to uncovered changed lines and `from_slop` picks untested files. `cleanup` builds an offline cleanup plan from dependency issues, the Slop Index, environment variables and weakened tests; `apply` performs only safe dependency fixes and needs `--allow-write`. `arch_diff` renders a Mermaid diagram of the internal imports the diff added and removed: green edges are new dependencies, red dashed edges are removed ones, and `fail_on_removed` returns exit code 1 when a dependency disappears. `roast` turns the diff into a technically grounded comedy roast in a chosen persona (linus, ramsay, corporate or default), cites file:line for every joke and ends with one real fix; it is model-backed and never edits files. `cinema` builds a terminal timelapse of the session from commits, runs, API calls, the last review and the receipt: a self-contained HTML player or an asciinema v2 cast, with no network, external assets or model call; `no_paths` hides subjects and finding locations. `bounty` scores every file from SAST findings, duplicated blocks, dead exports, aged TODOs and churn without tests, then renders an ASCII WANTED poster with the worst file and its reasons; deterministic and offline. `autopsy` performs a post-mortem on a commit: diff stats, SAST on added lines, weakened tests, mock leaks, ranked suspects and a before/after timeline; `fail_on_risk` returns exit 1 for a dangerous verdict. `echo` builds self-contained SVG badges from local stats, git history and the receipt (commits, agent runs, API calls, cache hits, findings and test status); `submit` sends only the nickname, window and aggregate numbers to an explicit `endpoint`, never paths, diffs or secrets, and there is no network by default. `sast` runs the deterministic static analysis over the change or over explicit `paths` and accepts `fail_on_issue`, `ignore` and `no_suppressions`; a finding at or above the gate is a normal result with exit code 1. `authz` checks route authorization over the change or explicit `paths` and accepts `fail_on_issue`, `ignore`, `public` and `no_suppressions`; a route finding at or above the gate is also a normal result with exit code 1. `preflight` returns one offline verdict over the planned change and accepts the same source flags (`diff`, `base`, `staged`, `unstaged`, `include_untracked`), plus `since`, `max_delta`, `fail_on_issue`, `no_secret_scan`, `no_sast`, `no_authz`, `no_deps`, `no_tests` and `no_slop`; a failed check is a normal result with `status: "fail"` and exit code 1, so the agent sees the failing check instead of a tool error. `ready` returns the offline agent readiness score 0-100 and accepts `fail_under`; a score below the threshold is also a normal result with exit code 1. `receipt_verify` recomputes the SHA-256 hash of the receipt, compares the recorded commit with HEAD and reports `ok`, `hashOk` and `stale`; a missing, edited or stale receipt is a normal result with `ok: false` and exit code 1, so an agent can see why the proof failed. The `fix` tool accepts `from_sast` and `from_authz` to repair security findings and rescan; the result then carries `sast` or `authz` with `{before, after, remaining}`. The server is read-only by default; start it with `--allow-write` to permit `fix` with `apply: true`, `commit` with `apply: true`, `test_fix` with a command, `stats` with `clear: true` and `mutate`, which rewrites source files temporarily. `test_gen` with `apply: true` also needs `--allow-write`. The `fix` result carries the unified `patch`, its `files` and `patchStats` (`additions`, `deletions`, `hunks`, `bytes`); patches over 200 000 characters are cut and marked with `patchTruncated` and `patchBytes`, so a host can show or apply the change without parsing the diff again.

`invariants` checks the diff against `.oc-pilot/invariants.md`

`hivemind` is an encrypted TCP mesh for sharing analysis work: `init` creates an ed25519 identity, `trust` pins a peer public key, `serve` accepts signed ECDH X25519 handshakes, and `send` transmits AES-256-GCM encrypted payloads. Only diffs, AST and LLM requests are allowed; executable payloads are rejected, and untrusted peers are dropped before any data is read.

`sandbox run <file>` executes one self-contained JavaScript or ESM file in `node:vm` with a separate context: static imports, `require`, `fetch`, `process.exit` and timers longer than a second are blocked, console output is captured, and execution is capped by `--timeout` and `--memory-limit`. TypeScript runs only from a built `dist/*.js`. This is not an OS sandbox for native code.

`honeypot deploy` plants decoy files — `.env.backup` with fake AWS keys, `src/utils/legacy/bypassAuth.ts` with a trapped `bypassAuth`, and `src/legacy/legacy_db_drop.ts` — and records them in `.oc-pilot/honeypot.json`. `preflight` fails with `[HONEYPOT TRIGGERED]: Agent attempted to bypass authentication using a trapped function. Session terminated. Trust score reduced.` when the diff imports, reads or changes a decoy. `honeypot status` lists the traps and `honeypot remove` deletes only marker files; the decoys are not real secrets.

`alien-dna` compares added diff lines with the repository architecture DNA at HEAD and fails with `[ALIEN DNA DETECTED]` when the change introduces a pattern that never appeared before (0% occurrence): Singleton, Proxy, dynamic RegExp, eval, global state, inheritance, decorators, Worker, EventEmitter, dynamic import, sync I/O or prototype mutation. The command is offline and deterministic, reads the baseline with git and never calls a model.

`hyper-chamber run <file>` ages one self-contained JavaScript or ESM file in `node:vm`: it fakes `Date.now`, accelerates timers, forces GC and samples the heap through `node:v8` while simulating up to a year of uptime in a short real budget. Sustained growth returns `[MEMORY LEAK DETECTED]: AI code survives Day 1, but crashes on Day N of simulated uptime.` The file must export `run`, `tick`, `main` or `default`; a plain script is wrapped and re-executed. This is a deterministic heuristic, not a proof, and native code is not supported.
`butterfly` runs the project test command under deterministic local chaos: `fetch` can return HTTP 500, add latency or broken JSON, and `fs` can return `EIO` for code under `--scope` (default `src/`). It reports injected fault counts, exit code and output tail; the test runner and `node_modules` are excluded by a stack filter, and database driver patching is best-effort. This is a test aid, not an OS sandbox.

`blindfold` obfuscates identifiers (`calculateDiscount(user)` becomes `fn_A(var_B)`) and sends only the stripped code to the model, asking for a strict JSON verdict. It fails with `[BLINDFOLD REJECTED]` when the model cannot explain the logic, finds a vulnerability, or confidence is below `--min-confidence`; `--dry-run` prints the mapping without a model call. It is a blind review, not a mathematical proof.

`antibody` learns from security findings: `antibody learn` scans the repository with the offline SAST engine and stores each finding as a signature (rule plus a normalized code snippet) in `.oc-pilot/antibodies.json`; `antibody scan` checks added diff lines against those signatures and fails with `[ANTIBODY MATCH]` when a known bad pattern returns. `antibody list`, `forget` and `clear` manage the store. It is a memory of past findings, not a replacement for a full SAST review.

`polygraph` checks the story against the code: it extracts the factual claims from a commit message or PR body and verifies each one against the diff. `test-added`, `file-added`, `file-removed`, `api-change`, `dependency`, `docs`, `security`, `behavior` and `refactor` claims get a deterministic check; `supported` means consistent with the diff, `contradicted` means the message promises something the diff does not do, and `unverifiable` means the diff cannot settle it. `[CLAIM CONTRADICTED]` exits 1, and `--strict` also fails on unverifiable claims. It reads the message, not the author's intentions.

`passport` records provenance instead of promises: `passport write` stores the commit, tree, changed files with SHA-256 or git blob hashes, the agent, the model and the checks you actually ran in `.oc-pilot/passport.json`, then binds the manifest with a digest. `passport verify` re-hashes the files and proves the manifest is still valid; a changed tree prints `[PASSPORT STALE]`, and an edited manifest prints `[PASSPORT TAMPERED]`. A commit passport stays valid for its immutable commit; a worktree passport is valid only while HEAD and the files are unchanged. A passport proves what was recorded, not that the code is correct.

`oracle` turns a refactor claim into a behavioral experiment: `oracle --command "node harness.mjs {input}" --input corpus.json` runs the same JSON cases on clean HEAD and on the diff in two shadow worktrees, then compares stdout and exit codes. Any difference prints `[BEHAVIOR CHANGED]` with the exact input and both outputs; identical results print `[BEHAVIOR SAME]`. The harness must be deterministic and read the `{input}` file. A same result covers only the supplied corpus, not every possible input.

`vaccine` turns a fixed bug into a permanent regression test. `vaccine create --fix HEAD` takes the fix commit and its parent, asks the model for one minimal test, then proves it in two shadow worktrees: the test must fail on the buggy parent and pass on the fix. Only verified vaccines are stored in `.oc-pilot/vaccines` with their metadata; `vaccine run` replays all of them on HEAD, and `list`, `forget` and `clear` manage the store. A rejected test is not a vaccine.

`mitosis` makes a large diff reviewable: `mitosis plan --strategy dir|file|type` partitions the change into an ordered commit sequence, and `mitosis apply --confirm` replays it in a shadow worktree, commits each group, optionally runs the test command after every commit, and exposes the result as a branch plus patch files in `.oc-pilot/mitosis`. Config changes come first, then source, tests and docs. If a commit fails tests, the branch stops there for inspection; a skipped test run is reported as skipped, not as a pass.

`intent` checks the change against the acceptance criteria: `intent check --criteria docs/acceptance.md` returns `met`, `partial`, `unmet` or `unverifiable` per criterion with evidence from the diff, and exits 1 on `unmet`. `intent sphinx --request "..."` runs before code: it lists missing questions, hidden assumptions and testable criteria, and prints `[REQUIREMENTS AMBIGUOUS]` when the request leaves decisions open. Both modes are model-backed; `met` means the diff supports the criterion, not that the feature is correct in production.

`scalpel` fixes a failure with the smallest change: give it a failing log (`--log`) or a command that reproduces the failure, and it asks the model for a minimal patch, applies the current diff plus the patch in a shadow worktree, runs the tests, and reports the blast radius — the symbols and references the patch touches. `[SCALPEL FIXED]` means the tests pass in the shadow; `--apply` writes the proven patch to the worktree. A rejected patch is never applied.

`mayday` handles the incident: `mayday bisect --good v1.2.0 --bad HEAD --command "npm test"` binary-searches the first commit where the check starts failing and prints its author, date and diff stat. `mayday rollback --to v1.2.0 --confirm` reverts everything after the target in a shadow worktree with `git revert`, runs the tests and exposes a reviewable branch. It never uses `reset --hard` or force-push; a failed rollback still leaves the branch for inspection.

`clairvoyant` predicts the CI scope: it maps changed files and exported symbols to tests that import them, reference their names or match the `*.test` naming convention, then returns the minimal subset in `[CI SCOPE]`. If nothing matches, it says to run the full suite instead of pretending the change is covered. It is a textual map, not a coverage proof.

`hemorrhage` proves or rejects a performance regression: it runs the same benchmark on HEAD and on the diff in two shadow worktrees, alternates the order, and compares medians, p95 and MAD. `--metric time` measures wall time, `--metric stdout` reads one number from the output, and `--direction higher` handles throughput. `[PERFORMANCE REGRESSION]` requires the change to exceed the threshold and the noise floor with a Mann-Whitney p below 0.05; a `same` verdict means this benchmark did not prove a regression, not that performance is fine everywhere.

`cuckoo` audits untrusted JS/ESM before you trust it: the file runs in an instrumented `node:vm` sandbox with mocked `fs`, `net`, `child_process` and `process`, and every attempt is recorded. `[CAPABILITY DENIED]` lists the capabilities it reached for; `process.exit` and static `import`/`export` stop execution, and `--allow fs,env` permits only named kinds. A clean run covers this file and this sandbox, not transitive native code or dynamic imports.

`chronos` reads a file's chronicle: commits, churn, fix/revert/incident/security markers, antibodies and vaccines, then scores it as a hotspot. `[HOTSPOT]` means the file has a history of fixes, rollbacks or incidents; inspect it before changing it and add a vaccine for the next fix. A low score is not proof that the file is safe.

`beacon` records a verification claim for a commit: `beacon stamp --check tests=pass --check preflight=pass --key beacon.key` stores the commit, tree, tool version, agent, model, commands, checks and a digest in `.oc-pilot/beacon.json`, then signs it with HMAC or `ssh-keygen`. `beacon verify` detects `[BEACON TAMPERED]` and `[UNATTRIBUTED]`; `beacon render --markdown` produces a PR comment. An unsigned beacon is valid but unattributed, so pass `--require-signature` in CI.

`quarantine` makes flaky-test suppression temporary: `quarantine add --test "auth flow" --owner alice --reason "race" --days 14` stores the test, owner, reason and expiry in `.oc-pilot/quarantine.json`; `quarantine check` prints `[QUARANTINE EXPIRED]` and exits 1 when the deadline passes. `list`, `remove` and `clear` manage the store. A quarantined test still exists and still fails; the entry only records who owns the fix and when the gate will force it.

`mirage` makes a test hermetic: `mirage record --command "node test.mjs" --cassette cassettes/login.json` runs the command with a preload that records every `fetch` response and `Date.now` value; `mirage replay` serves those responses from the cassette and fails with `[MIRAGE MISS]` on any unrecorded request. `list`, `show` and `clear` manage cassettes. It records `fetch` and the clock, not arbitrary sockets or native modules.

`warden` turns repository rules into code: `.oc-pilot/policy.json` can forbid paths (`package-lock.json`, `.env`), content (`eval(`), dependencies and extensions, require tests whenever source changes, and cap the diff size. `warden check` reports `[POLICY VIOLATION]` with rule, file and evidence and exits 1; `init` writes a sample policy and `show` renders the current one. It is deterministic and offline.

`tribunal` runs three separate reviewers — security, correctness and maintainability — and keeps only findings confirmed by at least two of them. `[TRIBUNAL CONSENSUS]` marks a confirmed issue, `[TRIBUNAL SPLIT]` marks a single-lens opinion, and `[TRIBUNAL CLEAN]` means no lens found anything. `--lenses`, `--min-consensus` and `--fail-on` control the panel. A split finding is a lead, not a verdict.

`skeptic` asks the model for a minimal executable test that should fail on the diff, applies the diff in a real shadow worktree, and runs the test on both the diff and clean HEAD. `bug` means the test fails on the diff and passes on HEAD; `clean` means the hypothesis was rejected; `unfalsifiable` means the test cannot distinguish the trees. A passing test never proves the absence of bugs.

`apoptosis` scans functions marked `/* @lifespan: 30d */`. When the marker is older than the lifespan and the symbol has no references, it reports `[Senescent]`; `apoptosis apply --confirm` comments those functions out in a shadow git worktree, runs the test command and lands the diff only if the suite is green. A failed run leaves the working tree untouched. It is a cleanup workflow for AI-written code, not an automatic guarantee that the function is unused at runtime.

`injection` scans the text an agent may read — README, docs, comments, HTML, JSON, YAML and source — for prompt-injection phrases, role hijacks, secret exfiltration, hidden unicode, CSS-hidden instructions, suspicious markdown images and base64 payloads. `--fail-on` controls the exit threshold, `--fix` strips invisible unicode, and `--include`/`--exclude` narrow the scan. It is a heuristic firewall, not a proof that the content is safe.

`query` runs a chainable AQL query against a lightweight code graph: `find(File|Function|Class|Import|CallExpression).where(field, value).sort(field).limit(n).select(fields...).count()`. It is not SQL and not a full TypeScript AST; it is a fast textual graph that the agent can probe before editing. MCP exposes it as `query_ast`.

`bankruptcy` forecasts technical debt from commit history: it scores each commit by weakened tests, SAST high/medium findings, added TODOs, churn and a slop proxy, smooths the daily series with a 14-day moving average, drops outliers and fits a linear regression. The output is the current score, slope, forecast date and a self-contained SVG chart; fewer than 10 commits returns `[INSUFFICIENT DATA: Need at least 10 commits to compute Slop Velocity]`. `--explain` prints the exact weights, where test weakening (0.35) and security (0.30) dominate.

`fix --shadow` and `battle --shadow` run the applied patch inside `.oc-pilot/shadow-tree`, a detached git worktree, so tests and external compilers see the modified files. The diff is extracted with `git diff` and applied to the real tree only when the run succeeds; a failed run leaves the working tree untouched. `--shadow` requires `--apply`.

`fuzz` discovers exported functions added by the diff and calls them with null, undefined, -1, 0, an empty string, a 10MB string, a `__proto__` object and empty containers. Every target runs in a separate Node process with a hard 2s timeout, a configurable heap cap and mocked fs/net/http/child_process; files that import side-effect modules are blocked before execution, and a crash or timeout is reported with the exact input. No model call.: each `## area` scopes its rules, `[CRITICAL]` marks a blocking rule, and rules whose area touches none of the changed files or their importers are skipped as `[SKIPPED: Out of scope]` without a model call. The model must answer strict JSON; verdicts are cached by the hash of diff and invariants, and violations are warnings by default. A CRITICAL violation or `--strict` / `--fail-on violation` returns exit code 3. `preflight --invariants` adds the same check to the gate.

`pack --hologram` builds a layered context instead of dumping the repository: LOD 0 keeps diff files complete, LOD 1 hides function bodies behind `body hidden` markers with `EFFECTS` hints and adds matching tests, LOD 2 lists export names only. Unbalanced braces fall back to full text with `[Hologram: parse bailout]`, and the final Markdown is secret-scanned. `zoom-symbol <file> <symbol>` returns one hidden body on demand; `pack_hologram` and `zoom_symbol` expose the same flow over MCP.

Every tool accepts `max_findings` (default 50; a capped result also carries `truncated` and `totalFindings`) and `verbosity` (`full` returns the JSON payload, `compact` returns a one-line summary and keeps the same data in `structuredContent`). When a client sends `_meta.progressToken`, the server emits `notifications/progress`; after `logging/setLevel` it also emits `notifications/message` per call. `--max-calls <n>` (or `OC_PILOT_MCP_MAX_CALLS`) caps model-backed calls per session, `0` disables the cap, and the offline tools `scan`, `fuzz`, `bankruptcy`, `query_ast`, `sandbox`, `hivemind_status`, `stats`, `slop`, `flaky`, `impact`, `deps`, `coverage`, `reviewers`, `test_guard`, `env_sync`, `mock_leak`, `ecosystem_verify`, `pack`, `pack_hologram`, `zoom_symbol`, `contract_drift`, `anti_regression`, `boundaries`, `test_plan`, `compliance_verify`, `brag`, `cleanup`, `arch_diff`, `roast`, `cinema`, `bounty`, `autopsy`, `echo`, `sast`, `authz`, `preflight`, `honeypot`, `alien_dna`, `hyper_chamber`, `butterfly`, `apoptosis`, `scan_injection`, `ready` and `receipt_verify` keep working after the budget is exhausted.

Configure a client automatically:

```bash
oc-pilot setup                      # every detected client
oc-pilot setup --client claude --local
oc-pilot setup --client cursor --global
```

The MCP server uses the configured engine. With `engine: "openai"` and `OC_PILOT_API_KEY` exported in the client's environment, no OpenCode installation is needed.

Start the server manually with an explicit project directory:

```bash
oc-pilot-mcp --cwd /absolute/path/to/project
# pinned for reproducibility:
npx -y oc-pilot@0.114.4 mcp --cwd /absolute/path/to/project
```

The `diff` and `log` tool arguments are text, not file paths. `paths` and `files` are project-relative and cannot escape the project directory. `context` is literal text, not an `@file` reference. `base` must be a git ref. `lang`, `fail_on`, `repo_context`, and `no_secret_scan` are available where the corresponding CLI command supports them.

The MCP server does not add its own file access: it runs the same CLI with `--cwd` fixed at startup. A client cannot point it at another directory through a tool argument.

### Streamable HTTP

For containers and remote agents, run the same server over HTTP instead of stdio:

```bash
export OC_PILOT_MCP_TOKEN="$(openssl rand -hex 24)"
oc-pilot-mcp --http --host 127.0.0.1 --port 8787 --path /mcp \
  --cwd /workspace --token "$OC_PILOT_MCP_TOKEN"
curl http://127.0.0.1:8787/health
```

MCP is **read-only by default**, over both stdio and HTTP: `scan`, `review`, `docgen`, `custom`, and patch-proposal `fix` work; `fix` with `apply: true`, `test_fix` that runs a new command, and `deps` with `fix: true` or `sbom` are rejected. Add `--allow-write` only for a trusted local client or an authenticated deployment. `oc-pilot setup --allow-write` adds the flag to generated client config.

The MCP endpoint sets `Mcp-Session-Id` on initialize. When `--token` is set, every request needs `Authorization: Bearer <token>` except `GET /health`. A non-loopback bind **refuses to start** without a token of at least 16 characters. Put a TLS-terminating reverse proxy in front of any public deployment.

## GitHub Action

The repository ships a composite action, so a pull request gate can be three lines:

```yaml
name: review
on: [pull_request]
jobs:
  oc-pilot:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: MyNameIsNikki/oc-pilot@v0.114.4
        with:
          command: scan
          args: --base origin/${{ github.base_ref }} --fail-on-secrets
```

Inputs: `command` (`scan`, `review`, `test-fix`, `docgen`, `custom`), `args`, `working-directory`, `annotations`, and `version` (install a published npm version instead of the action checkout). `scan` needs no API key. For a model-backed review, set the engine and provider environment variables on the step.

```yaml
name: oc-pilot
on: [pull_request]
jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: actions/setup-node@v4

```

`--github` turns parsed findings into inline `::error file=...,line=...` and `::warning` annotations. `scan` needs no API key and is suitable for a fast first gate. Add `--json` instead when a later step needs the structured report.

To upload results to GitHub Code Scanning, write a SARIF report and upload it:

```yaml
      - run: oc-pilot scan --base origin/${{ github.base_ref }} --format sarif -o oc-pilot.sarif
      - uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: oc-pilot.sarif
```

Each release is published from a tag by the repository's own workflow (OIDC trusted publishing with a provenance attestation; set the `NPM_TOKEN` secret to fall back to a granular npm token), and the GitHub release body is taken from the matching `CHANGELOG.md` section. CI runs the suite on Node 22 and 24 and prints an informational coverage table from `node --test --experimental-test-coverage` — no threshold, so a noisy signal never blocks a merge.

## Security model

- The built-in repo-context agent is read-only: `read`, `glob`, and `grep` only. `edit`, `shell`, `subagent`, web tools, and external directories are denied.
- Known secret files (`.env`, keys, SSH/AWS credentials, `.npmrc`, `.pypirc`) are denied.
- `--no-repo-context` uses an isolated temporary project with all tools denied and adds full changed files as text.
- Diff, rules, and full-file content are scanned before being sent to the model.
- Project rules and code comments are data, not instructions. The system prompt explicitly treats injected instructions as untrusted.
- The repo-context agent runs inside the analyzed project, so project-level OpenCode config and plugins may load. Use `--no-repo-context` for untrusted repositories.
- Only `fix --apply` writes to the working tree. It rejects patches that touch files outside the reviewed diff, checks the patch with `git apply --check`, saves a local snapshot under `.git/oc-pilot/snapshots/` before applying, runs the configured tests, and reverts the patch when they fail. It never commits or pushes.
- `install-hook` writes only managed hook files inside the git hooks directory, marks them with a header comment, keeps backups when `--force` replaces a foreign hook, and is fully reversible with `--uninstall`.
- The HTTP transport uses the MCP session header and an optional bearer token. Plain HTTP has no transport encryption; use a TLS proxy for remote deployments, and do not expose it without a token.
- No file is modified by `review`, `test-fix`, `docgen`, or `custom`.

## Limitations

- The quality of the review depends on the selected model and the context budget.
- A diff-only review cannot see every caller; use the OpenCode engine or repo context for contract changes. The `openai` engine sees the full changed files, not arbitrary call sites.
- Secret detection is pattern-based and can miss novel formats or produce false positives.
- Auto-detection of test commands may need `--command` / `testCommand`.
- Project-level OpenCode config is not loaded in isolated `--no-repo-context` mode.
- The CLI UI is currently Russian; the model prompt and output are available in English and Russian.
- `fix` works best with text patches. Binary files, renames, and CRLF-sensitive repositories may need a manual `git apply`.
- The HTTP server is single-tenant: anyone with the token can analyze and apply fixes in the mounted workspace. Run one container per trust boundary.
- `setup` edits MCP client config only; it does not install Node, OpenCode, or provider credentials.

### Regression tests

Three layers keep the contracts the model sees from drifting:

- `test/golden/` pins the built prompt input for fixed diffs, so section order, empty-value handling and secret redaction only change on purpose. Regenerate with `OC_PILOT_UPDATE_GOLDEN=1 npm test` and read the diff before committing.
- `test/fixtures/model-output/` holds realistic model replies; `src/core/output-format.test.ts` asserts which severity, location and text the CLI reports for each one.
- `normalizeLocation` collapses the location shapes models actually emit (`a.ts:10-14`, `a.ts:10,12`, `a.ts#L12`, `a.ts (line 10)` → `a.ts:10`), and bullets inside fenced code blocks are ignored when parsing.
